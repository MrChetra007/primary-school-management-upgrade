The Problem

School records are still paper-based and disconnected

  • No parent visibility — Parents only learn about their child's progress during exam week; no ongoing insight into daily scores or attendance
  • Fragile record-keeping — Paper score books are lost, damaged, or illegible over time; no backup exists
  • Unreliable rural internet — Teachers in Battambang province lose connectivity mid-class; cloud-only apps fail in practice
  • No cross-role visibility — The principal cannot review student performance trends without collecting physical reports from every teacher

Core Design Decision

Every user IS a teacher

In Cambodian schools, all staff members are teachers first. The librarian is a teacher who manages the library. The admin is a teacher who runs the school. This is not a UI convention — it is enforced at the database level.

teachers.user_id is NOT NULL UNIQUE — one profile per account, always linked. There is no such thing as a user without a teacher profile.

The role field in public.users only controls what they can access — not who they are.

Security

Role-Based Security

✓
Row-Level Security — Every table has RLS enabled. Policies use get_user_role() and get_user_school_id() helpers.
✓
Role scoping — A teacher sees only their own class. Admin sees their entire school. Super admin sees all schools.
✓
Narrow anon access — Parent portal users are anon; RLS is scoped to report_link_id — no open using (true) policies.
✓
Pending/rejected links hidden — Anon users cannot access report links with status = 'pending' or 'rejected'.

Appendix

How the Report Link Works

  1. Teacher requests approval on the ranking page → report_links.status set to 'pending'
  2. DB trigger creates notification for the admin — in-app bell icon, no email/push
  3. Admin approves or rejects with optional rejection note → teacher is notified via another DB trigger
  4. UUID acts as the shareable token — the URL path is /parent/report/:report_link_id
  5. RLS enforces anon access — only status = 'approved' links are visible to the anon role
create policy "report_links: anon read approved only"
  on report_links for select to anon
  using (status = 'approved' and
    school_id = get_user_school_id());
Honest answer

Forwarding the link still works — no expiry or PIN yet. Same tradeoff as a private video link. Acceptable for the pilot scope.

Appendix

How Offline Auth Works

  1. Session stored in localStorage by Supabase Auth client automatically
  2. INITIAL_SESSION event fires on boot to restore session from storage
  3. The bug: handleAuthEvent was skipping INITIAL_SESSION, relying on router guard init() — async timing gaps left session.value null
  4. The fix: handleAuthEvent now sets session.value and calls fetchProfile() immediately on INITIAL_SESSION; init() bails early if session already exists
const handleAuthEvent = (event, session) => {
  if (event === 'INITIAL_SESSION') {
    session.value = session;
    if (session?.user) fetchProfile(session.user.id);
    return;
  }
  // handle SIGNED_IN, SIGNED_OUT, TOKEN_REFRESHED...
};
Honest answer

Survives an app restart. Does not survive an expired token with no network — that requires a refresh token exchange.

Appendix

How the Offline Score Queue Works

  1. useNetworkStatus — reactive isOnline ref via navigator.onLine + browser events
  2. mutate() wrapper — drop-in replacement for supabase.from().insert/update/delete
  3. Online: passes through to Supabase immediately → returns result
  4. Offline: enqueues to localStorage with UUID → returns { queued: true }
  5. On reconnect: FIFO queue processed with progress/success/failure toasts
async function mutate(table, type, payload, filters) {
  if (isOnline.value) {
    return await supabase.from(table)[type](payload, filters);
  }
  const id = crypto.randomUUID();
  offlineQueue.enqueue({ id, table, type, payload, filters });
  return { queued: true, id };
}
Honest answer

Same record edited offline on two devices is not resolved yet — this is a listed roadmap gap.

Appendix

How Voice Replies Work

  1. MediaRecorder API — useVoiceRecorder composable wraps start() / stop() / upload() / playback()
  2. Captured audio is a .webm Blob — good browser compatibility, reasonable file size
  3. Blob uploaded to Supabase Storage (report-voices bucket) — URL saved to report_messages
  4. Same composable used for teacher notes and parent replies — consistent API
async function stopAndUpload(reportLinkId, studentId, role) {
  recorder.stop();
  const blob = await new Promise(resolve => {
    recorder.ondataavailable = e => resolve(e.data);
  });
  const path = `${reportLinkId}/${studentId}/${role}.webm`;
  await supabase.storage.from('report-voices').upload(path, blob);
  // Update report_messages row with the new URL
}

Why voice? Removes the typing barrier for parents who are uncomfortable writing about their child's schoolwork in Khmer.

Appendix

How the PWA Install Works

  1. vite-plugin-pwa generates the Web App Manifest + service worker at build time
  2. App is installable from the browser — "Add to Home Screen" on mobile, install icon in desktop address bar
  3. App shell is precached — all Vue components, router, stores, and assets load instantly without network
  4. Storage assets cached 30 days — profile pics, signatures, stamps, voices via CacheFirst strategy
  5. Updates require explicit user click — registerType: 'prompt'; new SW waits, user taps "Update" to activate
// vite.config.js
VitePWA({
  registerType: 'prompt',
  workbox: {
    runtimeCaching: [{
      urlPattern: /^https?:\/\/.*\/storage\/v1\/object\/.*/,
      handler: 'CacheFirst',
      options: { expiration: { maxAgeSeconds: 30 * 24 * 60 * 60 } }
    }]
  }
})
Honest answer

It's a PWA, not a native app — installable from the browser, no app store, no APK to distribute. Works offline for the cached app shell and score entry.
