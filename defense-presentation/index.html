The Problem

Cambodian public primary schools manage student data entirely on paper.

  • Paper-based records — attendance sheets, score ledgers, health cards stored in physical filing cabinets, prone to loss and damage
  • No software budget — most schools cannot afford commercial SIS solutions; government funding covers only basic infrastructure
  • Fragmented tracking — attendance, scores, health records, and growth data exist in separate unconnected paper systems
  • No parent engagement — report cards are handwritten and delivered months late; parents have no visibility into their child's progress
  • Manual year-end promotion — re-enrolling students into new classes each academic year is done by hand, error-prone and time-consuming

Why Not Existing Tools?

Generic solutions fail to address the specific realities of Cambodian public primary schools.

Excel / Paper

No access control, easy data loss, no concurrent multi-user support, no reporting automation, no parent access.

Commercial SIS

Too expensive for public schools (often $5–15/student/year). Requires internet always-on. No Khmer language or Cambodian calendar support.

Single-School Apps

No multi-tenant architecture — each deployment requires separate infrastructure. No centralized oversight for the Ministry of Education.

Database Indexing

An index is like a book's table of contents — it lets the database find records instantly instead of reading every row. With 25+ indexes on frequently-queried columns (school_id, student_id, date), a query that scans a school's 10,000 attendance records runs in milliseconds rather than seconds.

🔒
Row Level Security (RLS)

Every database query is automatically filtered by the user's role and school — a teacher's SELECT on the students table only returns their own class, even if the query asks for "all students." This is enforced server-side by PostgreSQL, not in application code, making it impossible to accidentally leak data across tenants.

"Every User Is a Teacher"

In Cambodian schools, all staff members — directors, librarians — are also teachers. The system reflects this reality.

  • Every account always has a matching teachers row
  • The role field controls only what you can access — not who you are
  • A director is a teacher who runs the school; a librarian is a teacher who manages the library
  • Unified profile means one source of truth for personal data, attendance, check-in times
  • Simplified account management via server-side Edge Function — a small backend API that runs on-demand in the cloud (similar to AWS Lambda). When an admin creates a user, the manage-user function atomically inserts 3 rows across separate tables (auth + public.users + teachers) in a single secure call, ensuring data integrity without exposing the database directly to the frontend.

Security Model

What is Row Level Security? In a traditional app, the backend code decides who sees what. RLS moves this logic into the database itself — every SQL query is wrapped with invisible filters based on who is making the request. For example, when a teacher loads their class list, PostgreSQL automatically appends WHERE teacher_id = current_user to the query. Even if a malicious request tried to fetch all students, the database would only return the ones that teacher is allowed to see. No application code, no middleware — the database enforces it directly.

Super Admin

Bypasses school RLS. Sees all schools, creates new tenants, manages platform-level operations.

Admin / Director

Scoped to school_id — manages classes, teachers, students, scores, budget, and inventory for their school only.

Challenges & Solutions

Challenge: Khmer Digit Parsing

Class names like ថ្នាក់ទី១ក (Grade 1A) use Khmer script numerals. The rollup system must extract numeric grades to promote students.

Solution: khmer_to_int() + extract_grade_from_class_name() PostgreSQL functions — map Khmer digits ᥐᥑᥒᥓ to Latin integers.

Challenge: Anon RLS Design

Parent portal uses Supabase's anon key — no login. Must grant data access without granting open read to the entire school database.

Solution: Every anon policy is scoped through report_links — a user knows a UUID, and RLS resolves it to a class, then to students, scores, and attendance. No open using (true) on sensitive tables.

Challenge: Teacher Check-In

Once-per-day attendance with automatic late detection based on configurable school shift times.

Solution: teacher_check_in() DB function compares check-in time against school_settings morning/evening thresholds and inserts with auto-calculated status. ON CONFLICT DO NOTHING enforces once-per-day at the DB level.
