Q1

What is this project about? What problem does it solve?

▼

This is a Primary School Management System designed specifically for Cambodian schools. It digitizes the entire school administration workflow — from student enrollment, attendance tracking, and score management to library management, budget tracking, and parent communication.

The core problem it solves: Cambodian rural schools still use paper-based systems for attendance, scoring, and reporting. Teachers spend hours manually calculating averages and rankings. Parent communication is limited to physical report cards distributed a few times per year.

Key innovations:

  • Offline-first design — works without internet (critical for rural Cambodia)
  • Link-only parent portal — parents access reports via a secure URL, no account needed
  • Khmer-language UI — fully localized for Cambodian users
  • Mobile-first PWA — installable on phones, works like a native app

What is unique about this system compared to generic school management software?

▼

Several things make this unique:

  1. Cambodia-specific — Khmer language UI, Khmer numeral support, Cambodian school structure (Grades 1-6, Monday-Saturday schedule)
  2. Offline-first — Teachers in rural areas with unreliable internet can still enter scores and data. Changes queue locally and sync when connection returns.

Q6

Why did you choose Supabase instead of Firebase or a custom backend?

▼

Several reasons:

  1. PostgreSQL database — Supabase gives you a real PostgreSQL database, not a NoSQL document store. This means we can use SQL joins, foreign keys, transactions, stored procedures, and complex queries. Firebase Firestore is NoSQL and would require denormalization.
  2. Row Level Security (RLS) — Supabase's RLS lets us enforce data isolation directly at the database level. Each query automatically filters by the user's role and school. With Firebase, this logic would live entirely in client-side code or Cloud Functions.
  3. Edge Functions — Deno-based serverless functions for user management (create/delete users with admin privileges). Firebase has Cloud Functions but they're Node.js-based and more complex to deploy.
  4. Realtime subscriptions — Built-in PostgreSQL replication for live notifications. Firebase has this too, but Supabase's is based on native PostgreSQL logical replication.
  5. Storage with RLS — File storage (profile pictures, voice recordings, signatures) with the same RLS policies as the database.
  6. Open source — Supabase is open source; Firebase is proprietary Google lock-in.
Key Point: The Supabase anon key is safe to expose in the frontend because all data access is protected by RLS policies enforced at the database level. The anon key cannot bypass RLS.
Q7

Why Vue 3 instead of React or Angular?

▼

Vue 3 was chosen for several practical reasons:

  1. Composition API — Vue 3's Composition API (<script setup>) provides excellent code organization for complex components. Logic is grouped by concern, not by type (data, methods, computed, lifecycle).
  2. Smaller learning curve — For a solo developer building a large application (81+ files), Vue's template syntax and reactivity system are more intuitive than React's JSX + hooks mental model.
  3. Single File Components (SFCs) — Template, script, and style co-located in one file. This is natural for a project with many role-specific views.
  4. Pinia integration — Official state management with excellent TypeScript support and devtools.
  5. Performance — Vue 3's proxy-based reactivity is faster than Vue 2's Object.defineProperty, and comparable to React's Virtual DOM.

Q10

How is the multi-tenant architecture implemented? How do you isolate data between schools?

▼

Multi-tenancy is enforced at three levels:

  1. Database level (RLS) — Every table has a school_id column. RLS policies use get_user_school_id() to automatically filter rows by the logged-in user's school. A teacher at School A can never see School B's data, even if they manually craft an API request.
  2. Application level — The auth.js store loads the user's school_id into memory. All Supabase queries include .eq('school_id', authStore.schoolId) as a filter.
  3. Edge Function level — The manage-user function receives school_id in the payload and stores it in the users table during account creation.
-- Example RLS policy (every table follows this pattern)
CREATE POLICY "admin manage own school"
  ON classes FOR ALL TO authenticated
  USING (
    get_user_role() = 'admin'
    AND school_id = get_user_school_id()
  )
  WITH CHECK (
    get_user_role() = 'admin'
    AND school_id = get_user_school_id()
  );

-- Helper function
CREATE FUNCTION get_user_school_id()
RETURNS uuid AS $$
  SELECT school_id FROM users WHERE id = auth.uid();
$$ LANGUAGE sql SECURITY DEFINER STABLE;
Q11

How does the User → Teacher data relationship work?

▼

The relationship follows a strict chain:

auth.users (Supabase Auth)
    ↓ id (cascade delete)
public.users ← role (super_admin/admin/teacher/librarian), school_id
    ↓ user_id (NOT NULL, UNIQUE)
teachers ← full_name, gender, dob, phone, degree, address, profile_url
    ↓ id
classes ← teacher_id → which teacher owns which class
    ↓ id
students ← class_id → which student belongs to which class

Key constraint: teachers.user_id is NOT NULL UNIQUE — every user must have exactly one teacher profile. The manage-user Edge Function always creates 3 rows in sequence: auth.users → public.users → teachers.

Cascade delete: If an auth user is deleted, their users row and teachers row are automatically removed via foreign key cascade.

Q14

How are scores stored? What is the difference between monthly and semester scores?

▼

Scores are stored as raw subject scores in the scores table. Each row represents one student's score for one subject in one period:

-- scores table structure
student_id  UUID     -- FK to students
subject_id  UUID     -- FK to subjects (via class_subjects)
month       INTEGER  -- 1-6 for monthly scores (null for semester)
semester    INTEGER  -- 1-2 for semester scores (null for monthly)
score       NUMERIC  -- Raw score (0-10)
academic_year_id UUID -- FK to academic_years

Monthly scores: Teacher enters per-subject scores for a specific month (1-6). The system calculates the monthly average as the arithmetic mean of all subjects.

Semester scores: Teacher enters exam scores. The semester average = (mean of monthly averages + exam average) / 2. Monthly averages are pulled from existing monthly scores.

Critical design decision: Score calculations happen on the frontend in scoreCalculator.js. The database stores raw scores only. This keeps the database simple and allows flexible calculation logic without migrations.

5. Authentication & Role-Based Access Control

Q16

How does the login and authentication flow work?

▼

Authentication uses Supabase Auth with email + password:

  1. User enters email + password on /login
  2. Frontend calls supabase.auth.signInWithPassword({ email, password })
  3. Supabase validates credentials and returns a JWT session token
  4. onAuthStateChange listener fires → auth.handleAuthEvent() is called
  5. fetchProfile() loads the user's row from public.users table (includes role and school_id)
  6. Also fetches the teachers row for the profile data
  7. Router guard checks the role and redirects to role-specific dashboard
// Login flow in auth.js store
async function login(email, password) {
  const { data, error } = await supabase.auth.signInWithPassword({ email, password })
  if (error) throw error
  // onAuthStateChange listener handles the rest
  return profile.value?.role
}

// Session backup system — survives PWA restarts
function backupSession(s) {
  localStorage.setItem('auth_backup', JSON.stringify({
    access_token: s.access_token,
    refresh_token: s.refresh_token,
    timestamp: Date.now()
  }))
}
PWA Session Persistence: The system has a dual session restore mechanism: Supabase's internal localStorage storage AND a custom backup in auth_backup key. If Supabase loses the session (e.g., tab killed during token refresh), the backup restores it within 7 days.
Q17

How does the router guard prevent unauthorized access?

▼

The navigation guard in router/index.js runs on every route change and performs 6 checks:

router.beforeEach(async (to) => {
  const auth = useAuthStore()

  // 1. ALWAYS await init() — guarantees session + profile are loaded
  await auth.init()

  // 2. Redirect logged-in users away from login/landing
  if (auth.isLoggedIn && (to.path === '/' || to.name === 'login')) {
    return { path: roleHome[auth.role] }  // → /admin/dashboard, /teacher/dashboard, etc.
  }

  // 3. Public routes — always allowed (landing, login, parent portal)
  if (isPublic) return true

  // 4. Auth Required Check — redirect to login if not authenticated
  if (requiresAuth && !auth.isLoggedIn) {
    return { name: 'login' }
  }

  // 5. Role Check — exact role match required
  if (to.meta.role && auth.role !== to.meta.role) {
    return { name: 'unauthorized' }
  }

  // 6. Academic Year Guard — admin must select year first
  if (auth.role === 'admin' && !yearStore.selectedYearId) {
    return { name: 'admin-academic-years' }
  }
})

Each route has metadata:

{
  path: '/admin/dashboard',
  meta: { requiresAuth: true, role: 'admin' }
}
// The guard checks: Is the user authenticated? Is their role exactly 'admin'?

This means a teacher cannot access /admin/* routes even by manually typing the URL — the guard will redirect to /unauthorized.

Q18

How are user accounts created? What is the Edge Function?

▼

User accounts are created via a Supabase Edge Function called manage-user, written in Deno (TypeScript on the server):

// Edge Function: supabase/functions/manage-user/index.ts
// Uses the SERVICE_ROLE key (bypasses RLS) for admin operations

// CREATE action:
// 1. Create auth user via supabaseAdmin.auth.admin.createUser()
//    - email_confirm: true (no email verification)
//    - user_metadata: { role, school_id }
//
// 2. Verify public.users row exists (created by DB trigger handle_new_user())
//    - If trigger failed, manually inserts as fallback
//
// 3. Create teachers row with full_name, gender, dob, phone, degree
//
// 4. If any step fails → rolls back by deleting the auth user (avoids orphans)

Why an Edge Function? Creating auth users requires the service_role key, which bypasses RLS. This key must NEVER be exposed in frontend code. The Edge Function runs server-side with the secret key, creating all 3 rows (auth + users + teachers) atomically.

6. Row Level Security (RLS)

Q19

What is Row Level Security and how does it protect data?

▼

Row Level Security (RLS) is a PostgreSQL feature that filters rows returned by queries based on the current database user's identity. In Supabase, every API request runs as the authenticated user (via their JWT), and RLS policies automatically filter the results.

Without RLS: If a teacher at School A manually crafted an API request for School B's students, Supabase would return all of School B's students. With RLS: The query returns zero rows because the RLS policy checks school_id = get_user_school_id().

-- Example: Student attendance table RLS

-- Super admin: full access to everything
CREATE POLICY "super_admin full" ON attendances
  FOR ALL TO authenticated
  USING (get_user_role() = 'super_admin');

-- Admin: full access within their school
CREATE POLICY "admin manage" ON attendances
  FOR ALL TO authenticated
  USING (
    get_user_role() = 'admin'
    AND school_id = get_user_school_id()
  );

-- Teacher: only their own class's students
CREATE POLICY "teacher own class" ON attendances
  FOR ALL TO authenticated
  USING (
    get_user_role() = 'teacher'
    AND student_id IN (
      SELECT s.id FROM students s
      JOIN classes c ON c.id = s.class_id
      WHERE c.teacher_id = (
        SELECT id FROM teachers WHERE user_id = auth.uid()
      )
    )
  );

-- Parent (anon): only via approved report link
CREATE POLICY "parent via report link" ON attendances
  FOR SELECT TO anon
  USING (
    student_id IN (
      SELECT s.id FROM students s
      JOIN report_links rl ON rl.class_id = s.class_id
      AND rl.status = 'approved'
    )
  );
Why this matters: Even if someone extracts the Supabase anon key from the frontend JavaScript, they cannot access any data that doesn't belong to them. The database itself enforces the access rules.
Q20

How does the parent portal work without login? How is it secured?

▼

The parent portal uses the anon (unauthenticated) role in Supabase — no login required:

  1. Teacher generates a report link on the Score Ranking page → report_links row created with status 'pending'
  2. Admin approves via the Approvals page → status changes to 'approved'
  3. Teacher shares the URL: /parent/report/:report_link_id
  4. Parent opens the link → sees a dropdown of all students in that class → selects their child
  5. Report card shows: scores + attendance + teacher message for that specific period

Security is enforced by RLS:

  • report_links has an anon SELECT policy: only 'approved' links are visible
  • scores, attendances, report_messages have anon policies scoped to report_link_id
  • Health, growth, vaccinations, sick days have NO anon policies — completely invisible to parents
-- Parent can only see data for students in approved report links
CREATE POLICY "anon read scores via report link" ON scores
  FOR SELECT TO anon
  USING (
    student_id IN (
      SELECT s.id FROM students s
      JOIN report_links rl ON rl.class_id = s.class_id
      AND rl.status = 'approved'
      AND rl.id = current_setting('request.jwt.claims', true)::json->>'report_link_id'
    )
  );

Q22

How does the approval flow for report links work?

▼

The approval flow is a 4-step process involving database triggers and real-time notifications:

1. TEACHER clicks "Request Approval" on /teacher/scores/ranking
   → report_links.status set to 'pending'
   → DB trigger creates notification: { type: 'approval_requested', ... }
   → Admin receives real-time notification via Supabase Realtime

2. ADMIN sees bell icon badge (unread count)
   → Opens notification dropdown
   → Clicks notification → navigates to /admin/approvals

3. ADMIN reviews the request
   → Clicks "Approve" → status = 'approved', approved_at = now(), approved_by = user_id
   → DB trigger creates notification: { type: 'approval_approved', ... }
   → OR clicks "Reject" with optional note → status = 'rejected'
   → DB trigger creates notification: { type: 'approval_rejected', ... }

4. TEACHER receives notification of decision
   → If approved: "Share Link" button unlocks
   → If rejected: sees rejection note, can revise and re-request

Real-time implementation: The notifications table is in Supabase's Realtime publication. The notifications.js Pinia store subscribes to postgres_changes on the notifications table, filtered by user_id. When a new notification is inserted (by a DB trigger), the frontend receives it instantly via WebSocket.

Q23

How does the Student Rollup work (year-end promotion)?

▼

The perform_student_rollup() PostgreSQL function handles year-end student promotion:

-- perform_student_rollup(p_old_year_id, p_new_year_id)
-- Returns: { success, total_promoted, total_graduated, details }

-- For Grades 1-5:
--   Copies students to the next grade's class in the new academic year
--   Auto-creates target classes if they don't exist
--   Original students are NOT moved (copy, not move)

-- For Grade 6:
--   Sets is_graduated = true (students leave the school)

-- Example: Grade 3 student in 2025-2026 → copied to Grade 4 class in 2026-2027

Key design decisions:

  • Copy, not move — Original students remain in the old year for historical records. New rows are created in the new year.
  • Auto-creates classes — If "Grade 4 Class A" doesn't exist in the new year, it's created automatically.
  • Khmer digit support — Students named with Khmer numerals (១, ២, ៣...) are parsed correctly.

Q25

How does the monthly score entry work? Explain the offline integration.

▼

The monthly score entry in ScoresMonthlyView.vue has two modes:

Full Grid Mode: A spreadsheet-like grid with students as rows and subjects as columns. Each cell is an input field. Scores support decimals (inputmode="decimal" for mobile keyboards).

Compact Mode: Horizontal subject tabs at the top, one subject at a time, with large touch-friendly inputs (44px min-height). Better for mobile phones.

// Score saving flow with offline support
async function saveAll() {
  const toUpsert = rows.value.map(row => ({
    student_id: row.studentId,
    subject_id: selectedSubject.value,
    month: selectedMonth.value,
    academic_year_id: yearStore.selectedYearId,
    score: row.score
  }))

  // useOfflineMutation transparently handles online/offline
  const result = await mutate('scores', 'upsert', toUpsert)

  if (result.queued) {

12. Offline-First Architecture & PWA

Q32

Explain the offline-first architecture in detail. How does it work?

▼

The offline system has two parts: offline writes (queue) and offline reads (cache).

1. Offline Write Queue:

// useOfflineMutation.js — transparent online/offline abstraction
async function mutate(table, type, payload, filters = {}) {
  if (isOnline.value) {
    // Online: direct Supabase call
    const result = await supabase.from(table)[type](payload)
    return result
  }

  // Offline: queue to localStorage
  queueStore.enqueue({ id: uuid, table, type, payload, filters })
  return { data: null, error: null, queued: true }
}

2. Queue Processing (on reconnect):

// offlineQueue.js — FIFO processing
async function processQueue() {
  const entries = [...queue.value]  // snapshot
  for (const entry of entries) {
    try {
      if (entry.type === 'upsert') {
        await supabase.from(entry.table).upsert(entry.payload).select()
      } else if (entry.type === 'insert') {
        await supabase.from(entry.table).insert(entry.payload)
      } // ... update, delete
      remove(entry.id)  // Remove on success
    } catch (e) {
      // Entry stays in queue for retry
    }
  }
}

3. Offline Read Cache:

// useCache.js — TTL-based localStorage cache
function get(key) {
  const raw = localStorage.getItem('sms_read_cache_' + key)
  if (!raw) return null
  const { data, expiry } = JSON.parse(raw)
  if (Date.now() > expiry) {
    localStorage.removeItem('sms_read_cache_' + key)
    return null  // expired
  }
  return data
}

// In score views:
// Online → fetch from Supabase, cache with 24h TTL (reference) or 2h TTL (scores)
// Offline → serve from cache, show yellow "Using cached data" badge

4. Connection Status Detection:

// useNetworkStatus.js — browser events
const isOnline = ref(navigator.onLine)
window.addEventListener('online', () => isOnline.value = true)
window.addEventListener('offline', () => isOnline.value = false)

Applied to: Monthly scores, semester scores, sick days, growth records, vaccinations.

Q33

How does the PWA (Progressive Web App) work? What is the service worker?

▼

The PWA uses vite-plugin-pwa with Workbox for service worker generation:

// vite.config.js — PWA configuration
VitePWA({
  registerType: 'prompt',  // Shows update prompt instead of auto-reload
  workbox: {
    globPatterns: ['**/*.{js,css,html,ico,png,svg,woff2}'],
    maximumFileSizeToCacheInBytes: 10 * 1024 * 1024,  // 10 MB
    runtimeCaching: [
      {
        // Supabase REST API: try network first, fall back to cache
        urlPattern: /^https?:\/\/.*\/rest\/v1\/.*/i,
        handler: 'NetworkFirst',
        options: { networkTimeoutSeconds: 5 }
      },
      {
        // Supabase Storage: cache first (images, fonts, voices)
        urlPattern: /^https?:\/\/.*\/storage\/v1\/object\/.*/i,
        handler: 'CacheFirst',
        options: { expiration: { maxAgeSeconds: 60 * 60 * 24 * 30 } }  // 30 days
      }
    ]
  }
})

Three caching strategies:

  1. Pre-cache — All static assets (JS, CSS, HTML, images) cached during service worker install (~161 entries)
  2. NetworkFirst — Supabase API calls try network first, fall back to cache after 5s timeout
  3. CacheFirst — Storage assets (profile pics, signatures, stamps, voices) cached for 30 days

Update flow: When a new service worker is available, usePwa.js shows a banner: "កំណែថ្មីមានហើយ!" (New version available!). User clicks "អាប់ដេតឥឡូវនេះ" (Update now) → service worker updates → page reloads.

vercel.json forces no-cache on sw.js and workbox-*.js to ensure users always get the latest service worker file.
Q34

Why is offline support limited to score entry and not all features?

▼

Offline support is intentionally scoped to the most critical teacher workflows:

  • Score entry — Teachers must enter scores on time regardless of internet. This is the highest-priority offline feature.
  • Sick days, growth, vaccinations — Secondary health data that teachers record during school hours.

Why not everything?

  • Attendance — Reverted to direct Supabase calls because attendance is time-sensitive and must be accurate in real-time
  • Budget, inventory, library — Used by admin/librarian who typically have stable office internet
  • Complexity — Every offline-enabled view requires cache invalidation, conflict resolution, and UI indicators. The ROI decreases for less-used features.

Future work: Extending offline to library borrows, budget, and inventory is listed in the roadmap.

14. Challenges & Solutions

Q41

What was the biggest technical challenge you faced? How did you solve it?

▼

The biggest challenge was the offline-first architecture. The core problem: teachers in rural Cambodia have unreliable internet, but they must enter scores on time.

Challenges encountered:

  1. Write queue sync — Initial implementation missed the upsert case in processQueue(). Score views exclusively use upsert (batch save). When the app came back online, queued scores were silently skipped and stuck in localStorage forever. Fixed by adding the missing case 'upsert' handler.
  2. Read caching vs empty states — When offline, score pages tried to fetch from Supabase, timed out after 5 seconds, then showed "No class assigned" — completely wrong. Fixed by implementing the useCache composable with TTL-based localStorage caching. Online → cache on success. Offline → serve from cache.
  3. PWA session loss — Users had to re-login after closing and reopening the PWA. Supabase's INITIAL_SESSION event was being skipped. Fixed by handling it in handleAuthEvent and adding a custom session backup system.
  4. Toast inconsistencies — 28 views had duplicate inline toast implementations with different icons and behaviors. Refactored to a single useToast composable + global ToastContainer.

15. Scoring Algorithm

Q45

How are scores calculated? Explain the algorithms.

▼

All calculations happen in src/utils/scoreCalculator.js:

1. Monthly Average:

function computeMonthlyAverage(scores) {
  // Filter out null/undefined/empty scores
  const validScores = scores.filter(s => s.score !== null && s.score !== '')
  if (validScores.length === 0) return 0
  // Simple arithmetic mean
  const sum = validScores.reduce((acc, curr) => acc + Number(curr.score), 0)
  return Number((sum / validScores.length).toFixed(2))
}
// Example: Math=8, Khmer=7, Science=9 → Average = 8.00

2. Semester Average:

function computeSemesterAverage(monthlyAverages, examAverage) {
  // Filter valid monthly averages
  const validMonths = monthlyAverages.filter(m => m !== null && m > 0)
  if (validMonths.length === 0) return examAverage
  // 50% monthly component + 50% exam component
  const monthlyAvg = validMonths.reduce((a, c) => a + c, 0) / validMonths.length
  return Number(((monthlyAvg + examAverage) / 2).toFixed(2))
}
// Example: Monthly averages = [7.5, 8.0, 7.8] → mean = 7.77
//          Exam = 8.5 → Semester = (7.77 + 8.5) / 2 = 8.14

3. Ranking:

function computeRank(students) {
  const sorted = [...students].sort((a, b) => (b.average || 0) - (a.average || 0))
  let rank = 1
  return sorted.map((student, i) => {
    if (i > 0 && sorted[i].average !== sorted[i - 1].average) {
      rank = i + 1  // Only increment if different from previous
    }
    return { ...student, rank }
  })
}
// Standard competition ranking: [9.5, 9.5, 8.2, 7.1] → [1, 1, 3, 4]
// Ties share rank, next rank skips numbers
Design decision: Scores are calculated on the frontend, not in the database. The DB stores raw scores only. This allows flexible calculation logic (e.g., changing the semester formula) without database migrations.

Q49

How does the toast notification system work? Why was it refactored?

▼

Before refactor: 28 views each had their own toast implementation — a ref(null) for the message, a showToast() function with setTimeout, and a template <div class="toast-container">. This led to inconsistent behavior, duplicate code, and different icons across views.

After refactor (v17):

// useToast.js — single module-level singleton
const toast = ref(null)  // Shared across ALL components
let timeout = null

export function useToast() {
  function showToast(msg, type = 'success', duration = 3000) {
    if (timeout) clearTimeout(timeout)  // Cancel previous
    toast.value = { msg, type }         // type: success|error|warning|info
    timeout = setTimeout(() => { toast.value = null }, duration)
  }
  return { showToast, toast }
}

// ToastContainer.vue — mounted ONCE in App.vue
// Renders the single active toast with consistent icons:
//   success → CheckIcon (green)
//   warning → ExclamationTriangleIcon (yellow)
//   info → InformationCircleIcon (blue)
//   error → XCircleIcon (red)

Every view now imports useToast() and calls showToast(). The ToastContainer renders it globally. One toast at a time, consistent styling everywhere.

How is Supabase client initialized? Why use custom storage?

Q55

If you were to start over, what would you do differently?

▼

Based on lessons learned:

  1. Automated testing from day one — Unit tests for composables, E2E tests for critical flows (login, score entry, parent portal). The manual testing approach works but is slow and error-prone.
  2. TypeScript — Would use TypeScript throughout for better type safety and IDE support. The current JavaScript codebase works but has no type checking.
  3. Consistent form validation — Would enforce vee-validate + yup on all forms from the start, instead of patching it in later.
  4. Standardized component patterns — Some views use different patterns for loading states, error handling, and data fetching. Would establish conventions earlier.
  5. Offline-first from architecture — Would design the data layer with offline support built-in from the start, instead of retrofitting it in Phase 12.

18. Rapid-Fire Quick Answers

Q56

What is the database used?

▼

PostgreSQL via Supabase. Supabase wraps PostgreSQL with additional features (Auth, Storage, Realtime, Edge Functions).

Q57

How many database tables are there?

▼

26 tables (schema v11). Core: schools, users, teachers, classes, students, scores, attendances, report_links, notifications.

Q58

What is the service worker's caching strategy?

▼

Three strategies: Pre-cache for static assets, NetworkFirst for API calls (5s timeout), CacheFirst for storage assets (30-day expiry).

Q59

How does the app handle Cambodia's Monday-Saturday school week?

▼

The attendance calendars and scheduling logic account for Monday-Saturday school days. Sundays are excluded by default from attendance marking and holiday calculations.

Q60

Why does the Supabase anon key appear in the frontend code?

▼

The anon key is designed to be public. It's a JWT that identifies the app but cannot bypass RLS. All data access is enforced by Row Level Security policies at the database level. The key only grants access that RLS allows.

Q61

What is Pinia? Why not Vuex?

▼

Pinia is the official Vue 3 state management library (replaces Vuex). It has simpler API, better TypeScript support, no mutations (only actions), and excellent devtools. Vue 3 documentation recommends Pinia over Vuex.

Q62

What is a Vue composable? Give examples from this project.

▼

A composable is a function that encapsulates reusable logic using Vue's Composition API. Examples:

  • useToast() — global toast notifications
  • useNetworkStatus() — reactive online/offline detection
  • useCache() — localStorage caching with TTL
  • useOfflineMutation() — offline-aware Supabase writes
  • usePwa() — PWA install/update state
  • useVoiceRecorder() — MediaRecorder API wrapper
Q63

How does the notification system work in real-time?

▼

Uses Supabase Realtime — a WebSocket subscription on the notifications table. When a DB trigger inserts a notification row, the frontend receives it instantly via postgres_changes subscription. The notifications.js Pinia store manages the subscription and unread count badge.

Q64

What are PostgreSQL database triggers used for?

▼

DB triggers automatically create notification rows when:

  • A teacher requests report link approval → trigger creates approval_requested notification for admin
  • An admin approves/rejects → trigger creates approval_approved or approval_rejected notification for teacher
  • handle_new_user() trigger creates a public.users row when a new auth user signs up
