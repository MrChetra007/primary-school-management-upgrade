Identity & Accounts

Why does everyone start out as the same kind of person?

Why every staff name tag says "Teacher"

One shared teachers table + role flags

At this school, every grown-up who works here wears the same starter name tag: "Teacher." Some teachers also carry a spare key — one opens the principal's office, another opens the library closet — but you have to be wearing the Teacher tag before you're allowed to carry any spare key at all.

In the app, the "name tag" is the teachers row every staff account gets, and the "spare keys" are the role flags (admin, librarian) layered on top of it.

Every staff account — director, admin, teacher, librarian — is one row in the teachers table. A role column decides which extra screens unlock, but the base row and its school_id are identical in shape for everyone. One permission system, one query pattern, one place to look — instead of separate admins and librarians tables that would each need their own security rules.

Every locker has exactly one name on it

users ↔ teachers, a one-to-one relationship

Every locker in the hallway has exactly one name on it, and every name has exactly one locker. Nobody shares a locker, and nobody's name floats around with no locker to call home.

The "locker" is a row in teachers, and the "name" is a row in Supabase's built-in users table — each points to exactly one of the other.

teachers.user_id holds a unique foreign key back to auth.users.id. Login and identity (email, password, session) live in users; everything about being staff at a specific school (name, role, school_id) lives in teachers. Splitting them lets Supabase Auth manage credentials without PSMS ever touching passwords, while teachers stays free to grow school-specific columns.

Multi-tenancy & Security

Why can't one school ever see another school's students?

One filing cabinet, hundreds of locked drawers

Row-Level Security — multi-tenant isolation

Picture one enormous filing cabinet in a basement, shared by every school in the country. Every drawer has its own lock. A teacher's key only opens the drawers for their own school — even standing right next to a hundred other schools' drawers, their key simply won't turn in anyone else's lock.

The "cabinet" is the single PSMS database, the "drawers" are rows in each table, and the "key" is the teacher's logged-in identity checked against a school_id column.

Every tenant-scoped table has a school_id column and an RLS policy like USING (school_id = (SELECT school_id FROM teachers WHERE user_id = auth.uid())). Postgres evaluates this on every row of every query, so even a raw SELECT * silently returns only rows matching the caller's school. One database, one schema — isolation enforced by the database engine itself, not app code.

The raffle ticket that only shows one prize

Anon / link-only access

A parent gets handed a single raffle ticket. No matter how many times they look at it, flip it over, or shake it, it only ever shows one prize: their own child's report card. It can't be swapped for anyone else's.

The "raffle ticket" is a link containing a unique report_link_id, and the "one prize" is the single student record that link's policy allows.

Report links use an unauthenticated (anon) key, so the RLS policy can't check auth.uid() at all. Instead it checks that the row's id matches the report_link_id embedded in the URL — a random, unguessable UUID acting as the password. No login, and critically, no way to browse to any other student's data.

The principal has to sign before it's mailed

Report link approval workflow

Before a letter goes home with the school's official stamp on it, the principal has to read it and sign it first. A teacher can write the letter, but she can't stamp it and mail it out by herself.

The "stamp" is a report link's status flipping to approved, and the "principal's desk" is an admin-only screen that must set it.

A teacher generates a report with status = 'draft'; RLS blocks the anon key from ever reading draft rows. Only an admin-role account can flip status to 'approved' — the exact moment the same row becomes visible through the public link's policy. The teacher prepares everything, but the "publish" transition is gated to a different role entirely.

Offline-first & Syncing

What happens when the classroom wifi drops?

Sticky notes on a corkboard

Offline write queue, drained FIFO

The classroom phone line goes down. Instead of giving up, the teacher writes each grade on its own sticky note and sticks it on a corkboard, in the order she writes them. When the phone line comes back, she doesn't shout them all out in a jumble — she reads them off the board one at a time, top to bottom, in exactly the order they went up.

The "corkboard" is a local queue of pending writes stored on the device. "Reading them out in order" is how that queue drains once connectivity returns.

The useOfflineMutation composable intercepts writes when navigator.onLine is false and appends them to an IndexedDB-backed queue instead of failing. Each entry keeps its timestamp and payload. An online listener triggers a drain function that replays queued mutations against Supabase strictly in insertion order — a grade entered at 9:01 never lands after one entered at 9:04.

First note written, first note read

Why the queue can't reorder itself

The sticky notes come off the board in exactly the order they went up — first note written, first note read out loud. Nobody's allowed to grab one from the middle of the stack and shout it out early.

"First written, first read" is FIFO — first-in, first-out — the ordering guarantee on the offline queue.

The queue is keyed by an auto-incrementing sequence number set at write time, not sync time. The drain loop always requests the lowest unsynced sequence number next and waits for it to succeed before advancing. This matters for dependent writes — a grade referencing an attendance record created five minutes earlier — where replaying out of order could violate a foreign key or overwrite a later edit with an earlier one.

The photocopy with a "good for 24 hours" stamp

Read cache with TTL

A teacher keeps a photocopy of today's class list in her bag, in case the office is closed when she needs it. The photocopy works fine for a while — but it has a stamp on it: "good for 24 hours." After that, it's too old to trust without checking again.

The "photocopy with a stamp" is cached read data with a stored fetch timestamp. "Too old to trust" is the cache's time-to-live expiring.

Read-heavy queries (rosters, subject lists) are cached in IndexedDB alongside a fetched_at timestamp. Under the TTL, the cache serves instantly with zero network round-trip. Over it, the cached copy still renders immediately — never a blank screen — but a background refetch replaces it. The write queue and read cache are deliberately separate systems with opposite failure modes: writes must never be lost, reads are allowed to be a little stale.

"Heads up — this might be old"

Stale-data badge

Taped to the photocopy is a small sticky note: "Heads up — this might be yesterday's list." Nobody mistakes the copy for the real, freshly-printed one.

The "sticky note" is a small UI badge shown whenever data is being served from an expired cache entry.

When a component renders from a cache entry older than the TTL, it sets an isStale flag alongside the data before the background refetch resolves. The UI reads that flag to render a small "may be out of date" badge, which disappears the instant the refetch completes and the store's timestamp updates — a visible admission of uncertainty rather than a silent guess.

Auth Persistence

Why doesn't closing the app log you out?

The amusement park wristband

Session token stored locally

At the amusement park gate, you get stamped with a wristband. You can leave the park, get lunch, come back, ride again — the gate remembers your wristband all day, no new ticket required.

The "wristband" is a signed session token (JWT) saved on the device. "The gate remembering it" is the app checking that token instead of asking you to log in again.

On login, Supabase Auth issues an access token and refresh token, which PSMS persists to storage rather than keeping only in memory. On every app start, the Supabase client reads the stored pair and silently re-establishes the session before any screen renders — a login screen only appears if no valid token exists at all.

Same wristband, walking in the next day

Why reopening the app doesn't log you out

Even if you go home and come back tomorrow with the same wristband still on your wrist, the gate remembers it and waves you through — as long as the wristband itself hasn't expired.

"The gate remembering it tomorrow" is the Supabase client firing an INITIAL_SESSION event from a stored, still-valid token, before the user does anything at all.

On boot, supabase.auth.onAuthStateChange fires an INITIAL_SESSION event carrying whatever session was restored from storage (or null). PSMS's router guard must wait for this event before deciding whether to redirect to login. The bug fixed in this project was the guard checking session state before INITIAL_SESSION had fired — so a perfectly valid stored session still bounced the user to login for a split second on cold start.

The wristband that quietly stopped working

Token expiring while offline

If your wristband quietly expired overnight, you don't find out until you walk up to the gate again and it beeps red. You looked like you were still wearing a valid wristband the whole time — it just wasn't actually working anymore.

The "beep" is a 401 response from Supabase the next time the token is actually used against the server, since there's no way to check expiry while fully offline.

JWTs carry their own expiry (exp claim), but an offline device can't ask Supabase to verify or refresh one — it can only optimistically trust the token it already has. The refresh token normally renews the session silently before expiry, but if the device stays offline past that window, the first request after reconnecting fails with a 401, triggering PSMS to attempt a refresh and, failing that, fall back to a real login screen.

Real-time & Notifications

How does the principal know the second something happens?

A bell wired to the mailbox

Supabase Realtime subscriptions

Instead of walking to the mailbox every five minutes to check for new letters, the mailbox has a little bell wired to it. The instant a letter drops in, the bell rings — nobody has to go looking.

The "bell" is a Supabase Realtime subscription over a WebSocket. "A letter dropping in" is a row being inserted into a watched table.

PSMS opens a supabase.channel(...) subscription filtered to postgres_changes on the notifications table for the current school_id. Whenever a matching row is inserted, Supabase's replication stream pushes the payload straight to the client over the open WebSocket — no polling loop, no repeated SELECT every few seconds burning battery and bandwidth.

Who rings the bell?

Database trigger

The bell is wired directly to the mailbox itself, not to any particular mail carrier. So it rings no matter who delivers the letter — the regular carrier, a substitute, or someone dropping it off by hand.

The "wiring" is a Postgres trigger on the source table. "No matter who delivers it" means the notification fires regardless of which part of the app made the write.

An AFTER INSERT trigger on tables like grades or attendance runs a function that inserts a matching row into notifications. Because the trigger lives in the database rather than any one client's code path, a grade entered from the mobile app, the web app, or a future admin import script all reliably produce the same notification — the guarantee lives below the application layer.

PWA & Service Worker

Why does the app feel instant, even offline?

A helpful assistant who remembers where the book is

Service worker

Imagine a helpful assistant standing between you and the school library. The first time you ask for a book, they walk and fetch it. But they remember exactly where it lives — so next time, they hand it to you instantly instead of walking there again.

The "assistant" is the service worker — a script that intercepts network requests. "Remembering where the book lives" is its cache of previously fetched files.

PSMS registers a service worker that intercepts fetch events for its own static assets (JS bundles, icons, fonts) and caches them on first load via the Cache API. Later loads are served straight from that cache before the network is even checked — the app shell appears instantly, even on a flaky connection, while actual data still goes through the separate read-cache/write-queue system.

The assistant waits for you to say "okay"

Prompt-to-update, not auto-update

You wouldn't want the library assistant to swap the book in your hands for a newer edition while you're mid-sentence. They wait until you say "okay, I'm ready" before handing you the new copy.

The "new edition" is a newly deployed app version. "Waiting for okay" is the update prompt shown instead of forcing an instant reload.

A new service worker version installs in the background but stays in a waiting state rather than activating immediately — activating would tear down in-flight requests and local state mid-session. PSMS listens for this event and shows a small "update available" prompt; only when the user taps it does the app call skipWaiting() and reload, guaranteeing updates never interrupt someone mid-entry.

Database Structure

How does the data actually connect together?

One teacher, many students

One-to-many relationship

One teacher has many students in their homeroom — but flip it around, and each student has only one homeroom teacher. It only works one way.

"One teacher, many students" is a one-to-many relationship — the most common shape in the whole database.

A students row stores a single homeroom_teacher_id foreign key pointing at one teachers row. "This teacher's students" is just WHERE homeroom_teacher_id = :id — no table needed in between, since the relationship only ever points in one direction.

The shared Math sign-up sheet

Many-to-many + junction table

Lots of classes take "Math," and "Math" is taught in lots of classes. So instead of every class writing "Math" fresh into its own private notebook, there's one shared sign-up sheet listing every class-and-subject pairing.

The "shared sign-up sheet" is a junction table — a table whose only job is to record pairs.

A class_subjects table holds just two foreign keys, class_id and subject_id, one row per valid pairing. Neither classes nor subjects needs to know about the other directly — adding a new pairing is one new row, not a schema change to either original table.

A hallway pass, not the whole file

Foreign keys

A student doesn't carry their entire file around the building. They carry a small hallway pass that just says which classroom they belong to — anyone can look up the rest from that one pointer.

The "hallway pass" is a foreign key — a column that stores just an id pointing at the row holding the real information.

A foreign key like students.homeroom_teacher_id → teachers.id stores a reference, not a copy. Postgres enforces referential integrity from it too: it rejects a value with no matching real row, and can cascade or restrict deletes — so a teacher can't be deleted while students still point at them, without an explicit decision about what happens next.

The library card catalog

Indexes

You could search every shelf, book by book, for one title. Or you could check the card catalog first and walk straight to the right shelf. The catalog doesn't hold the books — it just tells you exactly where to look.

The "card catalog" is a database index — a smaller, ordered structure built purely to make lookups fast.

PSMS indexes high-traffic lookup columns like students.school_id and grades.student_id, so Postgres binary-searches a compact B-tree instead of scanning every row. The tradeoff is real: an index speeds up reads but adds write cost, since every insert also updates the catalog — worth it on columns filtered constantly, wasteful on ones rarely queried.

Business Logic

How does the app decide what to show?

Two kids tie for first place

Rank computation with tie-skipping

Two kids cross the finish line at exactly the same time. They both get a "1st place" ribbon. Because two kids already took the 1st and 2nd spot between them, the very next kid down the line gets a "3rd place" ribbon — never a "2nd."

"Skipping straight to 3rd" is what a proper rank function does with ties, as opposed to just counting positions one by one.

Class rankings use Postgres's RANK() OVER (ORDER BY average_score DESC) rather than ROW_NUMBER(). RANK() gives tied rows the same value and skips the next rank accordingly (1, 1, 3), matching a real ribbon ceremony — whereas ROW_NUMBER() would arbitrarily break the tie and hand out a "2nd place" that doesn't reflect reality.

The scratch-pad average

Client-side calculated fields

The teacher's gradebook only ever writes down each individual test score. The class average is worked out fresh, every time someone asks, on a scratch pad off to the side — it's never written permanently into the gradebook itself.

The "scratch pad" is a computed value derived in the app at read time, never stored as its own column.

Fields like a student's average or class rank are computed in a Vue computed() (or a Postgres view, for heavier aggregates) from raw grades rows every time they're displayed, rather than stored redundantly on a students.average column. This guarantees the derived number can never drift out of sync — there's no second copy that could go stale after a grade is edited or deleted.
