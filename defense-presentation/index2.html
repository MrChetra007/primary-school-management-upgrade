PSMS Thesis Defense — Q&A Cheat Sheet

Primary School Management System · Vue 3 + Supabase · National University of Battambang · Defense: July 25, 2026
Real-Time & Notifications
Q: How do notifications reach the admin without refreshing?
A: Supabase Realtime — a DB trigger fires on insert into notifications (e.g. teacher requests approval). Frontend subscribes to that table via a realtime channel, so the bell icon's unread count updates live, no polling.
Q: Why triggers instead of creating notifications in frontend code?
A: A trigger guarantees the notification fires no matter which code path touches the table — frontend, Edge Function, or future admin tool. Frontend-only logic risks silent drops from bugs or bypasses.
PWA / Service Worker
Q: What is a service worker, in your own words?
A: A background script the browser runs separately from the page — it intercepts network requests and serves cached responses. That's what makes the app installable, offline-capable, and instant on repeat visits.
Q: Why change registerType from autoUpdate to prompt?
A: autoUpdate could swap code mid-session while a teacher is entering scores. prompt waits for explicit approval — an update banner appears, refresh only happens when the teacher chooses.
Q: Why cache-control no-store for sw.js and index.html specifically?
A: If the service worker file itself gets cached by CDN/browser, users get stuck on an old version permanently, unable to receive updates. Those files must always be fetched fresh.
Database Design & Performance
Q: Why 25+ indexes — how did you decide what to index?
A: Based on actual query patterns — anything filtered heavily in RLS policies or dashboards (school_id, class_id, student_id foreign keys) needs an index, or every tenant-scoped query does a full table scan as data grows.
Q: With 28 tables and a year of scores/attendance per student, will it scale?
A: Per-school volume stays modest (one school's population); multi-tenancy means growth is horizontal (more schools), not one school's tables growing unbounded. Honest gap: multi-tenant isolation hasn't been stress-tested under real concurrent load.
Process & Ownership
Q: Did you build all 81 files yourself?
A: Solo developer using AI assistance throughout — same as using an IDE, Stack Overflow, or pair programming. What matters: every architectural decision (RLS design, offline-first scoping, approval workflow) was mine, and I can explain and defend each one.
Q: How did you test without an automated test suite?
A: Manual testing at a real Battambang school with real teachers (Phase 8) — legitimate QA for a solo-built system at this stage. Acknowledge automated testing as a known gap, not something claimed as done.
Q: Why Vercel for deployment?
A: Zero-config deploys from Git, free tier suits a single-school pilot, pairs cleanly with Supabase's hosted backend — no server to manage myself.
Business Logic
Q: How does rank computation handle ties?
A: Ties share the same rank; the next rank skips accordingly (two tied for 1st → next is rank 3, not 2). Computed within each class only, never school-wide.
Q: Why is score calculation done client-side, not in the database?
A: The database stores only raw scores as the single source of truth. Averages/totals/ranks are derived values computed in one shared utility (scoreCalculator.js) — never stored redundantly, so a computed value can never drift from the raw data.
DB Relationships — One-to-One
Q: Where is there a strict 1:1 relationship, and why?
A: public.users ↔ teachers, via teachers.user_id NOT NULL UNIQUE — every account is exactly one person, one profile, never zero or many. Also auth.users ↔ public.users.
Q: Why enforce UNIQUE instead of careful application code?
A: App code can have bugs or race conditions. A unique constraint makes "one profile per account" impossible to violate even if a future feature forgets to check — a guarantee at the data layer, not a hope at the code layer.
DB Relationships — One-to-Many
Q: Give the core one-to-many chain in your schema.
A: schools → users → teachers → classes → students. Each school has many users; each teacher owns many classes (classes.teacher_id); each class has many students (students.class_id). This chain also enforces multi-tenancy — everything traces back to one school_id.
Q: Other 1:many relationships that matter?
A: students → scores/attendances/growth/vaccinations/sick_days — one student accumulates many timestamped records. classes → report_links → report_messages — one link per month/semester, one thread per student.
Q: Why not store scores as columns on the student row?
A: One score per subject per month per year is inherently repeating data — exactly what a separate scores table with foreign keys is for. Columns would need schema changes every new month.
DB Relationships — Many-to-Many
Q: Where is there a many-to-many relationship, and how modeled?
A: classes ↔ subjects, via junction table class_subjects. A class has many subjects; the same subject (e.g. "Math") is taught differently per class/grade, so subjects are pulled per-class, not from one global list.
Q: Why not give subjects a class_id directly?
A: Subjects are still a shared, reusable pool per school (e.g. "English" exists once). A junction table lets many classes reference the same subject without duplicating rows.
Q: Any other many-to-many?
A: students ↔ books via book_borrows — a student borrows many books over time, a book is borrowed by many students. The junction table also carries its own data (borrow date, return date) — a sign of a proper many-to-many with attributes.
Cascade Behavior & Referential Integrity
Q: What happens to a teacher's classes if their account is deleted?
A: auth.users deletion cascades to public.users, then to the teachers row (user_id FK). classes.teacher_id is ON DELETE SET NULL — the class survives with teacher_id = null, not deleted. In practice, staff are deactivated (status='inactive') rather than hard-deleted, to avoid orphaning classes and students.
Q: How do you stop a student from belonging to a class in a different school?
A: Every table in the chain carries its own school_id (not just inherited through joins), and RLS policies check school_id directly on each table rather than trusting the relationship chain alone — so a bug in one join can't leak cross-tenant data.
Self-Referencing / Hierarchical
Q: Any hierarchical or self-referencing relationship?
A: No classic self-reference (like manager-employee), but academic_years functions similarly — each year's classes are cloned from the prior year via clone_classes_structure(), giving a conceptual "previous year → current year" lineage without a literal self-FK.
ER Diagram Walkthrough — Narrative Answer
school_id (tenant root) └─ auth.users → users → teachers (identity) └─ academic_years → classes → class_subjects → students (academic structure) └─ scores, attendances, health, growth, vaccinations, sick_days (student activity, 1:many each) └─ report_links → report_messages (parent portal) └─ notifications (approval workflow) └─ teacher_phrases (per-teacher, cross-cutting)
"Everything scopes to school_id at the top. Identity flows auth.users → users → teachers. Academic structure is academic_years → classes → class_subjects → students. From students, everything else branches out — scores, attendance, health, sick days, growth, vaccinations — each its own one-to-many, since a student accumulates many of each over time. Cross-cutting features — report_links/messages for the parent portal, notifications for the approval workflow, teacher_phrases per teacher — each scope to whichever entity owns them."
